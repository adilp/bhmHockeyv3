# Game results: the compatibility audit

The rule: nothing in this change may crash or break the app people already
have installed. The installed app is a fixed client. This document is the proof,
rule by rule, with the evidence and how to re-run it.

The audit therefore treats the installed client as the **union** of the API
calls in `packages/api-client` at `dfced95` and at `60977b7` (126 distinct
calls; every 1.0.5 call is also in the 60977b7 set). The list, each joined to
the server endpoint and its pinned shape: `docs/game-results/installed-client-calls.md`.

How that client parses responses (`packages/api-client/src/client.ts` and the
services): plain axios JSON, typed by TypeScript only. There is no runtime
schema (no zod/yup/io-ts anywhere in `packages/` or `apps/mobile/`), so an
unknown field would be ignored - but this change adds none to any existing
response anyway. Two behaviors that matter: **a 401 from any call logs the
user out** (`client.ts` response interceptor), and errors are turned into a
plain `ApiError` object.

## 3. The migration

`20261127194158_AddGameResults`, generated by `dotnet ef migrations add`:

- **Creates** `GameResults`, `GamePlayerLines`, `GameGoals` (+ 10 indexes on
  those new, empty tables) and **adds** `Users.HideGameStats boolean NOT NULL
  DEFAULT false`. Nothing else: no `AlterColumn`, `Drop*`, `Rename*`.
- **No table rewrite.** PostgreSQL 11+ stores a constant column default in the
  catalog; existing `Users` rows are not rewritten. The new indexes are on empty
  tables.
- **Locks.** `ADD COLUMN` takes a brief ACCESS EXCLUSIVE lock on `Users`; the
  new foreign keys take SHARE ROW EXCLUSIVE on `Events`, `Organizations`,
  `Users`. All are held only until the migration's transaction commits (well
  under a second on an idle table). The migration starts with
  `SET LOCAL lock_timeout = '5s'`, so if a long transaction is holding `Users`
  it **gives up after 5 s instead of queuing the app's own queries behind it**.
- **Atomic and safe twice.** EF runs the migration in one transaction and
  records it in `__EFMigrationsHistory`; a second start applies nothing (step F).
  The SQL scripts `docs/game-results/AddGameResults.up.sql` / `.down.sql` are
  idempotent and were each applied twice (`scripts/game-results/rollback-sql-check.sh`).
- **A written way back**: `docs/GAME_RESULTS_RUNBOOK.md`, "Roll back". The
  normal way back is the code only (old code runs on the new schema, proven);
  the down script drops the new tables and the column and is the last resort
  (it deletes published results).

### How migrations run in production, and what a failure does

`Program.cs` calls `db.Database.Migrate()` at startup, before the app serves,
and in Production **re-throws** a migration error, so the process exits.
`.do/app.yaml`: one `api` service, `deploy_on_push: true` from `main`, Docker
build of `apps/api`, health check `/health` (initial delay 60 s, 3 failures).
On App Platform the new container must pass its health check before traffic
moves to it; a container that exits never does, the deployment is marked
failed, and the previous deployment keeps serving (DigitalOcean's documented
behavior for a failed deploy; not something this repository can test).

Measured here (step G): with another session holding a lock on `Users`, the
new API's migration hit the lock timeout after ~5.8 s, rolled back whole (no
table, no column, no history row), and the process aborted. The old API then
started and served on the untouched schema. So a failed migration is a failed
deploy, not an outage - **provided** the previous deployment keeps serving,
which is DigitalOcean's behavior, not this code's.

## 4. Startup and health, in the order the deployment really uses

App Platform starts the NEW container while the OLD one is still serving, the
new one migrates, then traffic switches. So for a window both run, and the old
code runs on the migrated schema. Both directions were run for real:

| case | result (`startup-compat-check.mjs`) |
|---|---|
| NEW code, un-migrated database (the deploy) | migrates exactly `AddGameResults`, `/health` 200, installed-client GETs byte-identical (C) |
| OLD code, migrated database (the deploy window, and a code rollback) | starts, `/health` 200, GETs byte-identical, registers a user (the INSERT omits `HideGameStats`; the default fills it) and creates an event (E) |
| NEW code, already migrated (any restart) | `Pending migrations: 0`, `/health` 200 (F) |
| NEW code, migration blocked | exits; schema untouched; old code serves (G) |

Local engine: PostgreSQL 16.14 (production's spec says 15; nothing here
depends on a 16-only feature: catalog defaults are 11+, `lock_timeout` 9.3+).

## 5. The audit table

`docs/game-results/installed-client-calls.md`: 126 calls; 125 reach an
endpoint whose snapshot line is unchanged; 1 (`POST /auth/logout`) has no
route on the server before or after (a 404 both ways, unchanged).

### Strongest evidence

1. Zero deleted or modified lines in any existing API file other than four
   additive edits (`User.cs` +1 property, `AppDbContext.cs` +3 DbSets and a new
   configuration method, `Program.cs` +5 registrations, the model snapshot).
2. The same 28 GETs return byte-identical bodies from the old and new server
   on the same real database, and the old server keeps working on the
   migrated schema.
3. A reflection snapshot of all 137 endpoints' full shapes, taken before the
   change, still matches; it is a test, so a later change that alters one fails CI.

### Weakest evidence

1. **Which OTA bundle phones run is unknown.** The audit covers the union of
   1.0.5 and `60977b7`; a phone on an OTA built from an unmerged branch would
   not be covered. Ask the owner which commit the last `eas update` was
   published from (`eas update:list --branch production`, the owner's command).
2. **DigitalOcean's failed-deploy behavior is documented, not tested.** If a
   deploy ever did swap to a container that then failed, the old container is
   gone; the migration's fail-fast design limits that to "the new container
   exits before serving".
3. Production data volume and concurrent load were not reproduced; the lock
   behavior was measured on a small local database.
4. The 28 recorded GETs cover the read paths with seed data, not every write
   path; the write paths are covered by the snapshot (shape) and the zero-diff
   (behavior), not by a recorded comparison.
